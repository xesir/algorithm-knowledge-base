## 算法原理

`std::list` 是 C++ 标准库里的**双向链表**：每个元素单独分配一个结点，结点里存「数据 + 前驱指针 + 后继指针」。因此任意位置的插入、删除都是 $O(1)$，但**不支持随机访问**，也没有 `operator[]`。

它在语法上是完整的，但在 OI 里几乎不用。原因不是「功能不够」，而是**理论优势换不来实际收益**：

1. **缓存局部性极差**。结点在堆上逐个分配，地址不连续。遍历时每一步都可能是一次缓存未命中，CPU 无法像遍历 `vector` 那样预取连续内存。
2. **每个结点都带额外开销**。除了数据本身，还要存两个指针和堆管理信息；每次插入是一次 `new`/`malloc`，删除是一次释放，单次常数远大于数组下标移动。
3. **有更好的替代**。真需要链表结构时（邻接表、可持久化结构、需要精细控制结点关系），标准做法是**数组模拟静态链表**：开 `e[N]`、`ne[N]`（必要时加 `pre[N]`），用下标代替指针。

一句话：`list` 的 $O(1)$ 插入在纸面上成立，但在卡常语境下，它带来的缓存与分配开销通常比省下的移动更贵。这也和「用数组模拟 `stack` / `queue`」是同一个逻辑——能被数组以更低常数替代的封装容器，自然退居次要位置。

## 语法速查

```cpp
#include <list>
list<int> lt;
```

| 类别 | 用法 | 说明 |
|---|---|---|
| 访问 | `lt.front()` / `lt.back()` | 首/尾元素，**没有 `lt[pos]`** |
| 插入 | `lt.push_front(x)` / `lt.push_back(x)` | 头/尾插入，$O(1)$ |
| 删除 | `lt.pop_front()` / `lt.pop_back()` | 删头/删尾，$O(1)$ |
| 插入 | `lt.insert(pos, x)` | 在迭代器 `pos` 前插入 |
| 删除 | `lt.erase(pos)` | 删除迭代器 `pos` 处的元素 |
| 清空 | `lt.clear()` | 清空所有元素 |
| 容量 | `lt.empty()` / `lt.size()` | 是否为空 / 元素个数 |
| 排序 | `lt.sort()` | 链表自带归并排序，**不能用 `std::sort`** |
| 合并 | `lt.merge(other)` | 合并两个有序链表 |
| 剪切 | `lt.splice(pos, other)` | 把 `other` 的结点剪到 `pos` 前，不拷贝 |
| 删除值 | `lt.remove(x)` | 删除所有值为 `x` 的元素 |
| 去重 | `lt.unique()` | 删除**相邻**的重复元素 |

注意 `size()` 在某些旧实现里是 $O(n)$ 的，需要频繁求长度时自己维护计数。

## 逐行代码解析

```cpp
lt.push_back(x);
lt.insert(lt.begin(), y);
lt.erase(lt.begin());
```

- `push_back(x)` 在尾部新分配一个结点，把原来的尾结点与它互连，$O(1)$。
- `insert(lt.begin(), y)` 在头结点前插入，同样是改几个指针，不移动任何已有元素——这正是 `list` 唯一真正的优势。
- `erase(lt.begin())` 释放头结点并把新的头结点前驱置空，$O(1)$。

```cpp
lt.sort();
lt.merge(other);
lt.splice(pos, other);
```

- `sort()` 是链表自带的归并排序，$O(n\log n)$，且不需要随机访问；用 `std::sort` 会编译失败。
- `merge(other)` 要求两链表都有序，直接把结点接起来，$O(n+m)$。
- `splice(pos, other)` 把 `other` 的整条链「剪」到 `pos` 之前，只改指针、不复制元素，$O(1)$——这是 `list` 里最有价值的一个操作。

```cpp
lt.unique();
lt.remove(x);
```

- `unique()` 只删**相邻**重复，想对所有重复生效必须先 `sort()`。
- `remove(x)` 会遍历整条链并删除所有等于 `x` 的结点，$O(n)$。

## 适用场景

**适合**：

- 需要在**已知迭代器位置**频繁插入/删除，且完全不需要随机访问；
- 需要 `splice` 这种「把一段结点整体搬到另一处、不复制」的语义（如把多个有序链表合并、LRU 缓存）。

**不适合**：

- 任何需要按下标访问的场景——`list` 没有 `operator[]`，只能从头走；
- 数据量大的遍历型操作，缓存不友好的代价会吃掉所有理论优势；
- OI 中绝大多数链表题（邻接表、静态链表、手写可持久化）——**用数组模拟更快也更可控**。

## 复杂度分析

| 操作 | 复杂度 |
|---|---|
| `push_front` / `push_back` | $O(1)$ |
| `insert` / `erase`（已有迭代器） | $O(1)$ |
| 按位置查找 | $O(n)$ |
| `sort` | $O(n\log n)$ |
| `splice` | $O(1)$ |
| `merge` | $O(n+m)$ |

空间上每个元素额外承担两个指针和堆块头部，$n$ 个 `int` 的实际占用远大于 `vector<int>` 的 $4n$ 字节。

## 常见陷阱与注意事项

- **不能用 `std::sort`**，只能 `lt.sort()`。
- **没有随机访问**，`lt[i]` 编译不过；取第 $k$ 个要 `advance` 从头走。
- **迭代器失效规则**：插入不会让其他迭代器失效，删除只让被删元素的迭代器失效——这点比 `vector` 宽松，但容易误判。
- **`unique()` 只处理相邻重复**，跨位置重复要先排序。
- **`size()` 可能是 $O(n)$**，频繁调用很伤。
- **内存碎片**：大量小结点反复分配释放，长期运行的程序容易碎片化。

## 对比与扩展

| 容器 | 随机访问 | 中间插入删除 | 缓存友好 | OI 常用度 |
|---|---|---|---|---|
| `vector` | $O(1)$ | $O(n)$ | 好 | 极高 |
| `deque` | $O(1)$ | 两端 $O(1)$ | 较好 | 高 |
| `list` | 不支持 | $O(1)$ | 差 | 极低 |
| 数组模拟静态链表 | 不支持 | $O(1)$ | 好 | 高 |

- **与静态链表对比**：静态链表用预分配的 `e[]`、`ne[]`、`pre[]` 存同样信息，没有动态分配、内存连续、行为可预测，是 OI 里真正会用的「链表」。
- **与 `deque` 对比**：如果只是需要两端快速增删，`deque` 的访问和缓存表现都更好，没有理由用 `list`。
- **什么时候仍会用 `list`**：需要 `splice` 语义、且结点数量不大、对常数不敏感时；或者纯粹为了让代码读起来接近「链表」的教科书描述。

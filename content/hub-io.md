## 算法原理

输入输出优化解决的是**数据规模大时标准 I/O 成为瓶颈**的问题。竞赛中常见的现象是算法复杂度已经达标，但读写耗时占比过高，导致超时。本大类目前收录快速输入输出（fast I/O）的常用写法与注意事项。

判断是否需要优化的依据：

- 输入数据量达到百万级及以上。
- 输出行数极多，且每行内容很短。
- 算法本身已经接近时限，I/O 成为可压缩的常数。

如果数据量很小，直接使用 `cin`/`cout` 或 `scanf`/`printf` 更安全，代码也更易读。

## 核心公式 / 状态定义与转移方程

快速 I/O 的核心是减少函数调用与格式解析开销：

1. 关闭 C 与 C++ 标准流的同步（`ios::sync_with_stdio(false)`）。
2. 解除 `cin` 与 `cout` 的绑定（`cin.tie(nullptr)`）。
3. 需要更快时，用 `getchar`/`fread` 手写整数读入，用 `putchar`/`fwrite` 手写输出。
4. 输出量很大时先把结果写入缓冲区，最后一次性输出。

这些手段不改变算法复杂度，只降低常数；是否值得使用取决于数据规模与代码可读性的权衡。

## 复杂度分析

快速 I/O 不改变渐进复杂度，只改变常数因子。实际收益取决于：

- 输入规模与单个整数/字符串的长度。
- 编译环境与标准库实现。
- 是否同时使用了 `endl` 这类强制刷新操作。

在百万级整数输入下，手写读入通常明显快于未关闭同步的 `cin`；数据量较小时差异可以忽略。

## 适用场景

- 输入包含大量整数、浮点数或短字符串。
- 输出行数极多，标准输出频繁刷新。
- 算法已经优化到极限，仍差常数时间。
- 不适合：交互题（需要及时刷新缓冲区）、数据量很小、代码可读性优先的教学场景。

## 常见陷阱与注意事项

- 交互题使用快速输出缓冲区却忘记刷新，导致判题器读不到输出。
- 手写读入没有处理负号、EOF 或多测。
- `ios::sync_with_stdio(false)` 与 `scanf`/`printf` 混用，导致读写顺序错乱。
- 输出缓冲区开得太小或越界。
- 使用 `endl` 频繁刷新，抵消了优化收益。

## 对比与扩展

输入输出优化属于工程技巧，与算法本身正交。它与语法技巧中的输入输出冷知识、调试技巧相邻：调试时关闭优化便于定位问题，提交前再打开优化。真正决定性能上限的仍然是算法复杂度与数据结构选型。
